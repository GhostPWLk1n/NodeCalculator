# Правки после v1.2.0 (Table / TableViewer / String)

## Версия

`package.json` обновлён с `1.3.0` до **`1.4.0`** (minor - новая
функциональность, без поломки обратной совместимости). `v1.3.0` был
опубликован на GitHub как первая собранная под Windows сборка
("first build") — всё, что описано ниже как "Раунд 14" и далее
(удаление конкретной связи вместо очистки всех, замена связи на занятом
сокете, боковая панель настроек ноды, редизайн Table/TableViewer/
ListInput/Percentage, минимальная ширина 200px для всех нод, нода
"Диаграмма Ганта"), сделано ПОСЛЕ этой публикации и составляет разницу
между `v1.3.0` и `v1.4.0`. `@version` во всех файлах синхронизирован с
`package.json` (`1.4.0`) — при каждом следующем релизе обновляется
единым проходом по всем файлам (см. `docs/NODE_API.md`, раздел 2.1).

Ниже — все доработки и багфиксы поверх первоначального внедрения типов
String/Data и нод Table/PercentageNode (раздел "Новые возможности v1.2.0"
ниже), в порядке раундов правок.

## Раунд 1 — вид StringNode, переполнение Table, новая нода TableViewer
- `stringNode.js` переписан по образцу `numberNode.js`: компактная
  однострочная нода (`nodeManager.js` навешивает класс
  `string-node-compact`, CSS-блок в `styles.css` зеркалит
  `.number-node-compact`), категория в сайдбаре — "Ввод", не "Служебная".
- `tableNode.js`: контейнеры строк столбца (`table-column-row`,
  `table-column-line`) не имели `display:flex` ни в CSS, ни инлайн —
  сокет-`<div>` (блочный по умолчанию) переносился на свою строку и ломал
  раскладку. Добавлены явные inline flex-стили на все ряды.
- Новая нода `tableViewerNode.js`: вход Data, выходов нет, тип Viewer.
  Рендерит `<table>` с заголовками колонок и значениями через
  `Helpers.formatByType()`; заголовок ноды подхватывает имя источника.
- Зарегистрирована в `main.js`, добавлен пункт в `index.html`.

## Раунд 2 — цвет сокета String при подключении, реальная причина переполнения Table
- `renderer.js`/`styles.css`: CSS-правило "серой заливки по умолчанию"
  (`.socket.socket-connected.output/input-socket:not(.socket-list)…`) не
  исключало `.socket-string`/`.socket-data`, а за счёт более длинной
  цепочки `:not()` имело более высокую специфичность, чем цветные правила
  — побеждало вопреки порядку в файле. Добавлены исключения
  `:not(.socket-string):not(.socket-data)`.
- Настоящая причина переполнения `TableNode` по ширине: `content.style.
  minWidth` был жёстко привязан к ВНЕШНЕЙ ширине ноды (`this.width`), а не
  к реально доступному месту внутри паддингов (`box-sizing:border-box`).
  Заменено на `width:100%` с независимым минимумом — как в
  `percentageNode.js`. Тот же баг был и в `TableViewerNode` — исправлен.
- `tableViewerNode.js` перенесён из раздела "Таблицы" в "Визуализация";
  добавлен вертикальный скролл с "прилипающим" заголовком; для колонок
  формата `percent` в ячейке появилась линейная заливка-графа под текстом.

## Раунд 3 — фильтрация неподключённых столбцов, адаптивная высота Viewer
- `tableNode.js` `calculate()`: столбцы без подключённого LIST-источника
  ("заготовки" для следующего соединения) больше не попадают в
  `tableData` — иначе Viewer и `PercentageNode` показывали пустой столбец.
- `tableViewerNode.js`: высота области прокрутки считается по фактическому
  числу строк (до 8 строк без скролла, дальше скролл) вместо фиксированных
  260px; добавлены номера строк и кнопка-глазик, скрывающая их.
- `tableNode.js`: убран `padding-left:22px` у второй строки столбца — он
  сдвигал String-сокет от края, из-за чего тот не был вровень с
  LIST-сокетом сверху; дефолтная ширина ноды уменьшена 320→300px.

## Раунд 4 — лимит столбцов, свободный ресайз Viewer, названия строк

- `tableNode.js`: чекбокс "имена" у каждого столбца — если включён и у

- `tableNode.js`: у каждого столбца добавлено поле ручной ширины (px,

## Раунд 5 — фиксированная ширина номеров, сортировка, редизайн строки столбца
- `tableViewerNode.js`: столбец номеров строк — фиксированной ширины,

- `tableViewerNode.js`: клик по заголовку столбца сортирует строки
  (по возрастанию → по убыванию → как есть, три состояния по кругу,
  иконка `↕`/`↑`/`↓`) — чисто визуально, исходные данные в `TableNode`
  не меняются; индекс сортировки сбрасывается, если набор столбцов
  источника изменился.
- `tableNode.js`: раскладка строки столбца пересобрана в
  `[String-сокет][имена][формат][ширина]` одной строкой (было раскидано
  по двум строкам с лишним лейблом "Столбец N"); `select` формата убрал
  `flex:1` (был избыточно растянут) — теперь компактные 56px; чекбокс
  "имена" получил `accent-color` под тёмную тему вместо белого нативного
  вида.

## Раунд 6 — Table/TableViewer не сворачивались, позиция ручки resize
- Настоящая причина: `TableNode`/`TableViewerNode` (и эталонный
  `exampleNode.js`) задавали `display:flex` ИНЛАЙН на `.node-content`, а
  инлайн-стиль без `!important` всегда побеждает CSS-класс — правило
  `.node.collapsed .node-content{display:none}` не срабатывало, контент
  никогда не скрывался. Фикс на двух уровнях: добавлен `!important` в
  само правило сворачивания (защищает вообще любую будущую ноду), плюс
  убран избыточный inline `display`/`flex-direction` из всех трёх файлов.
- `styles.css`: ручка изменения ширины ноды (`.node-resize-handle`) была
  `right:2px; bottom:2px` (внутри границ, перекрывала угол содержимого).
  Заменено на `right:-1px; bottom:-1px` — внешний край ручки теперь ровно
  на 1px выступает за пределы ноды по обеим осям.

## Раунд 7 — баг сохранения/загрузки .ncp после обновления схемы нод
- `layoutManager.js` `loadFromData()`: убрана строка
  `if (sn.inputs) node.inputs = sn.inputs;`. Она насильно перезаписывала
  уже корректно вычисленное конструктором `node.inputs` СОХРАНЁННЫМ (и
  потенциально устаревшим) числом. Пока у каждой ноды число входов было
  константой, это было безобидным no-op — но `PercentageNode` в этой
  сессии получил второй вход (1→2), а `TableNode`/`OperationNode` сами
  вычисляют `inputs` из `inputSockets.length`/`config` в конструкторе.
  Загрузка `.ncp`, сохранённого ДО этих изменений схемы (например, старый
  файл с `percentage`-нодой и `inputs:1`), откатывала `node.inputs`
  обратно на 1, рассинхронизируя его с `inputSockets` (длина 2).
  Конструктор каждой ноды и так корректно выставляет `inputs` из
  `config` — отдельная перезапись была лишней и в данном случае вредной.

## Раунд 8 — новая нода: Проценты от суммы (percentConvertNode.js)
- Обработчик LIST → LIST: каждый элемент входного списка заменяется на
  его долю (%) от суммы всех элементов, имена сохраняются
  (переиспользует готовый геттер `ListData.percentages`).
- Не путать с `PercentageNode` (рисует диаграмму) - этот узел только
  преобразует данные, результат можно подключить куда угодно, например,
  в столбец `TableNode`.
- Переопределяет `getValueFormat()` → `'percent'` (хук из `baseNode.js`,
  раздел "Новые возможности v1.2.0") - потребители с форматом "Авто"
  (например, столбец `TableNode`) сами подхватывают, что на выходе
  проценты, без ручной настройки. Каждый элемент выходного списка также
  несёт `format:'percent'`.
- Добавлена в раздел сайдбара "🔧 Преобразование", тип `percentConvert`,
  запись в `Constants.TYPE_NAMES`.

## Раунд 9 — итоги, decimals, группировка тысяч, фикс наложения sticky-заголовка
- `tableNode.js`: у каждого столбца новое поле `totalType`
  (`null`/`sum`/`max`/`min`/`avg`) - select "Сум/Бол/Мин/Сред" сразу после
  формата; и `decimals` (0-10, `null` = авто) - вынесено в отдельную
  строку 3 вместе с шириной, чтобы не перегружать строку 2. Оба поля
  прокидываются через `TableData` (сериализуются автоматически - они
  часть объекта `column`, отдельных правок в `layoutManager.js` не
  потребовалось).
- `dataTypes.js`: `TableData.aggregate(col)` - вычисляет итог по столбцу
  (сумма/наибольшее/наименьшее/среднее), нечисловые значения игнорирует,
  `null` без `totalType` или без чисел.
- `tableViewerNode.js`: строка "Итого" (`<tfoot>`) рендерится, только если
  хотя бы у одного столбца задан `totalType`; для остальных столбцов без
  итога ячейка пустая. Прилипает к низу обёртки при скролле (`position:
  sticky; bottom:0`), как заголовок прилипает к верху.
- `helpers.js`: `formatByType()` пробрасывает `decimals` в новую
  `formatGrouped(value, decimals)` - число со **пробелами**-разделителями
  тысяч (`1000` → `"1 000"`) и заданным числом знаков после запятой;
  `formatNumber()` (используется в редактируемых полях ввода) не тронут -
  группировка там была бы не к месту.
- **Фикс "таблица налезает на заголовки":** `border-collapse: collapse`
  в связке с `position: sticky` на ячейках - известный баг рендеринга
  Chromium (визуальные артефакты/наложение при скролле прилипающих
  ячеек). Заменено на `border-collapse: separate; border-spacing: 0`.

## Раунд 10 — точная высота скролла TableViewer, стиль resize-хэндла, компактный TableNode
- `tableViewerNode.js`: `applyWrapHeight()` считал высоту окна прокрутки
  по приблизительным константам (`HEADER_HEIGHT`/`ROW_HEIGHT`) и
  вызывался ДО того, как таблица вообще появлялась в DOM - то есть не
  знал ни настоящих размеров шапки/строки, ни того, будет ли строка
  "Итого" (`tfoot`). Из-за этого окно оказывалось то на строку заголовков
  ниже (константа не совпадала с реальной высотой шапки), то на строку
  итогов короче (`tfoot` вообще не учитывался). Теперь высота считается
  ПОСЛЕ вставки таблицы в `wrap`, по настоящим `offsetHeight` шапки,
  первой строки тела и `tfoot` (если есть) - никаких магических констант.
- `styles.css`: нативный resize-хэндл (`resize: both`) обёртки таблицы
  раньше рисовался браузером как диагональная иконка-уголок, выбивавшаяся
  из тёмной темы. Добавлено `.table-viewer-wrap::-webkit-resizer` -
  серая точка (`border-radius:50%`), согласованная по цвету/hover с
  `::-webkit-scrollbar-thumb`.
- `tableNode.js`: раскладка строки столбца сведена к двум строкам вместо
  трёх - `[LIST-сокет][имена][формат][итог][✕]` и
  `[String-сокет][px][зн:]`. Дефолтная ширина ноды уменьшена 340→300px.

## Раунд 11 — меньше точка resize, гарантированно непрозрачный фон sticky-ячеек
- `styles.css`: `.table-viewer-wrap::-webkit-resizer` переведён с
  `border-radius:50%` (заливает весь бокс резайзера, который у браузера
  крупнее, чем нужно визуально) на `radial-gradient` с явным радиусом
  5px - управляемый размер точки, независимый от фактического размера
  нативного бокса.
- `tableViewerNode.js`: все sticky-ячейки (шапка, номера строк, "Итого")
  переведены с сокращённого `background: var(--md-surface-variant)` на
  `background-color: var(--md-surface-variant)` + `will-change:
  transform` - гарантированно непрозрачный фон и отдельный композитный
  слой. Это известная особенность рендеринга `position: sticky` в
  Chromium: прокручиваемый контент иногда "просвечивает" сквозь
  sticky-ячейки даже при номинально непрозрачном цвете фона -
  `border-collapse: separate` (раунд 9) решал только часть симптома.

## Раунд 12 — архитектурный отказ от position:sticky в TableViewerNode
- `tableViewerNode.js` переписан: вместо одной `<table>` со sticky-шапкой
  и sticky-футером внутри общей прокручиваемой области - три физически
  раздельных блока в обычном потоке документа: `headerRow` (обычный
  поток), `bodyScroll` (собственный `overflow-y:auto`, только он и
  прокручивается вертикально), `footerRow` (обычный поток, ниже тела).
  Раунды 9-11 патчили СИМПТОМЫ известной особенности рендеринга Chromium
  у `position:sticky` (border-collapse, `background-color`+`will-change`)
  - этот раунд убирает саму причину, полностью отказавшись от sticky.
- Столбцы у всех трёх блоков выровнены не через `<table>`-раскладку и не
  через JS-синхронизацию скролла, а через явные одинаковые пиксельные
  ширины ячеек (`numColWidth` для номеров строк, `col.width` или
  эвристика по длине заголовка для остальных) - `getColumnWidths()`.
- Горизонтальный скролл - на внешней обёртке (`.table-viewer-wrap`,
  `overflow:auto`): `bodyScroll` не ограничивает свою ширину, поэтому её
  "вылезание" по горизонтали ловит внешняя обёртка, и шапка/тело/футер
  скроллятся синхронно одним нативным скроллом ("двойной overflow").
- Высота `bodyScroll` (`flex:1; min-height:0; max-height:<computed>`)
  считается ТОЛЬКО по строкам тела - шапка и футер физически вне этой
  области и в расчёт вообще не входят, что и убирает саму причину бага
  "на строку заголовков ниже / на строку итогов короче" на уровне
  архитектуры, а не приближённой оценки размеров.

## Раунд 14 — контекстное меню: "Очистить соединения" → "Удалить связь"
- Раньше пункт меню "🔗 Очистить соединения" был доступен только через
  правый клик по НОДЕ и стирал ВСЕ соединения проекта разом
  (`connectionManager.clearAll()`), без привязки к конкретной ноде или
  связи. Теперь правый клик по САМОЙ ЛИНИИ соединения открывает то же
  меню с единственным пунктом "🔗 Удалить связь", который удаляет именно
  эту связь (`connectionManager.removeConnection(...)`, уже
  существовавший метод, просто не был доступен из UI для одной связи).
- `renderer.js`: `createConnectionPath()` теперь строит ПАРУ элементов -
  невидимый широкий `hitArea` (`stroke-width:14`, `pointer-events:stroke`,
  ловит клик/наведение) и видимую тонкую линию `path`
  (`pointer-events:none`, чисто декоративная) - по родной 2.5px линии
  сложно попасть правой кнопкой мыши, hitArea даёт удобную область
  клика без изменения визуальной толщины линии. Наведение на hitArea
  подсвечивает связь (толще + непрозрачнее) - видно, что удалишь.
  `drawAllConnections()` при перерисовке удаляет старые hitArea вместе
  со старыми path (иначе накапливались бы при каждом пересчёте графа).
- `connectionManager.js`: новое поле `contextMenuTarget` (конкретное
  соединение, а не просто id ноды) и `showConnectionContextMenu(x, y,
  conn)` - показывает общее меню, скрывая пункты, относящиеся к нодам.
- `nodeManager.showContextMenu()`: наоборот, скрывает "Удалить связь" и
  сбрасывает `connectionManager.contextMenuTarget` - режимы "выбрана
  нода" и "выбрана связь" взаимоисключающие.
- `index.html`: всем пунктам меню присвоены `id` для программного
  переключения видимости; глобальный обработчик закрытия меню (клик
  вне его пределов) сбрасывает обе цели.

## Раунд 15 — занятый сокет: замена связи вместо отказа
- `connectionManager.js` `finishConnection()`: раньше перетаскивание
  новой связи на уже занятый вход отклонялось целиком ("⚠️ Вход уже
  занят"), и приходилось сперва вручную удалять старую связь. Теперь,

## Раунд 16 — сборка под Windows: фикс "Cannot create symbolic link" (winCodeSign)
- `electron-builder` при СБОРКЕ ПОД WINDOWS всё равно пытается скачать
  `winCodeSign` (инструмент подписи для macOS) из-за автообнаружения
  сертификата подписи (`CSC_IDENTITY_AUTO_DISCOVERY`). Архив
  `winCodeSign-2.6.0.7z` содержит symlink'и на `.dylib`-файлы, а Windows
  без прав администратора/Developer Mode не даёт их создавать - сборка
  падала на распаковке этого архива, хотя для чисто Windows-инсталлятора
  он вообще не нужен.
- `package.json`: все `dist*`-скрипты теперь запускаются с
  `CSC_IDENTITY_AUTO_DISCOVERY=false` (через `cross-env`, новый
  devDependency - чтобы переменная окружения ставилась одинаково что в
  cmd, что в PowerShell, что в bash) - отключает автообнаружение
  сертификата и, соответственно, необходимость в `winCodeSign` для
  Windows-сборки.

## Раунд 17 — боковая панель настроек ноды (InspectorManager)
- Новый модуль `core/inspectorManager.js` - правая боковая панель,

  ноды наружу, чтобы нода оставалась компактной.

  результату (типы поля: `text`/`color`/`select`/`number`/`checkbox`).
- `baseNode.js`: базовая схема (доступна ЛЮБОЙ ноде без переопределения)
  - поле "Имя" (дублирует переименование двойным кликом по заголовку,
    но доступно и из панели) и новое поле "Цвет узла" - акцентная
    полоска слева (`box-shadow: inset`, не влияет на layout), сбрасывается
    отдельной кнопкой "↺" к цвету темы по умолчанию.
- `numberNode.js`: дополняет базовую схему полем "Формат значения"
  (Число/Деньги/Проценты) - та самая отложенная "тонкая настройка",
  которую в самом начале решили не встраивать в тело ноды, а вынести в
  будущую боковую панель (см. `BaseNode.getValueFormat()`, раздел
  "Новые возможности v1.2.0" ниже). Другие ноды могут добавить это поле
  себе по тому же образцу.
- `nodeManager.js`: `selectNode()`/`deselectNode()` (класс

- `color`/`valueFormat` сериализуются в `.ncp` как обычные поля ноды

## Раунд 20 — TableViewerNode: один ресайз-хэндл вместо двух + новая нода "Диаграмма Ганта"
- **Убран дублирующий хэндл ресайза.** У `TableViewerNode` раньше было
  два независимых способа менять размер: общая ручка ноды (только
  ширина) и нативный `resize:both` на `.table-viewer-wrap` (ширина+
  высота) - по сути одно и то же в разных углах. Теперь ресайз только
  через общую ручку ноды, но для неё сделано исключение: если нода
  реализует `beginFreeResize(el)`/`applyFreeResize(el, deltaY)`, та же
  самая ручка тянет и высоту тоже, в обход общего правила "высота только
  по контенту" (`nodeManager.js`) - осознанное исключение, а не
  нарушение. Курсор ручки становится диагональным
  (`.node-resize-handle.free-resize`) для таких нод.
  `TableViewerNode.applyFreeResize()` передаёт дополнительную высоту в
  `.table-viewer-wrap` (`wrapHeight`, сериализуется в `.ncp`) - строк
  показывается больше/меньше без пересоздания DOM.
- **Новая нода: `ganttNode.js` - "Диаграмма Ганта"** (раздел сайдбара
  "Преобразование", тип `gantt`). Вход 0 - LIST задач (имя = задача,
  значение = длительность в часах или днях, единица - в панели). Задачи
  по умолчанию ставятся последовательно друг за другом от даты начала
  плана; полосу любой задачи можно перетащить мышью по горизонтали -
  новое начало запоминается по имени задачи (`this.taskDates`) и
  переживает пересчёт графа и сохранение проекта. Вход 1 - альтернативная
  готовая таблица (Data): если её заголовки содержат "начало"/"окончание"
  (`isCompatibleTable()`), нода использует её НАПРЯМУЮ для отрисовки,
  без пересчёта из списка - так на вход можно подать её же собственный
  выход, отредактированный в другом узле. Выход - Data-таблица
  (Задача/Начало/Окончание/Длительность). Боковая панель (раздел
  "Календарь"): дата начала плана (`type: 'date'` - новый тип поля в
  `InspectorManager`), период отображения (Месяц/Квартал/Полгода/Год),
  единица длительности (Часы/Дни). Дат-хелперы (`addDays`/`formatDateRu`/
  `parseDateRu`/`daysBetween`) - без внешних библиотек, чистый `Date`.

  константа - прокидывается через `buildRuler`/`buildTaskRow`/

- Дедлайн плана (`deadlineDate`, поле типа `date` в панели) - красная
  вертикальная линия (`buildDeadlineLine()`) поверх линейки и строк,

- `layoutManager.js`: `rulerScale`/`showGridLines`/`deadlineDate`

- **Треугольная ручка дедлайна.** Отдельная узкая строка над шапкой

  раньше даты начала плана - осмысленное состояние ("план уже сорван"),

- Боковая панель: 4 новых чекбокса ("Показывать год/месяц/число/день

- `layoutManager.js`: `showYearRow`/`showMonthRow`/`showDayRow`/

## Раунд 24 — система бейджей-плашек над нодой (фаза 0b плана Досок/Дашбордов)
- Второй самостоятельный кусок плана "Доски" - общий, переиспользуемый
  механизм оповещений, а не одноразовый костыль под конкретно дашборд-
  несовместимость. Тот же паттерн, что `getInspectorSchema()`/
  `getDashboardWidget()`: хук на `BaseNode`, конкретные ноды им пользуются.
- `baseNode.js`: `getStaticBadges()` (свойство ТИПА ноды, для подклассов)
  + `addBadge(key, {type, text})`/`clearBadge(key)`/`getBadges()`
  (динамические, обычно из `calculate()`, ключ - чтобы разные проверки
  не затирали бейджи друг друга) + `getActiveBadge()` - выбирает ОДИН
  самый важный по приоритету (`error > warning > beta/deprecated >
  info`), при равенстве приоритета статический бейдж побеждает
  динамический (статические идут первыми в объединённом списке).
- `constants.js`: `BADGE_PRIORITY`/`BADGE_SHORT_LABELS` - централизованно,
  как `VALUE_FORMATS`. `helpers.js`: `badgeShortLabel(type)`.
- `renderer.js`: `syncNodeBadge(node, el)` - централизованная точка
  синхронизации DOM-плашки (создание/обновление/удаление), не в
  `node.updateDisplay()` - многие ноды переопределяют его без `super()`,
  бейдж просто не показался бы для части нод. Вызывается и из
  `updateAllDisplays()` (на каждый пересчёт), и из
  `nodeManager.renderNode()` (сразу при создании - иначе статический
  бейдж вроде "beta" не был бы виден до первого пересчёта графа).
- `styles.css`: чип-плашка `position:absolute; top:-18px;` над заголовком,
  цвет по типу; `error` дополнительно даёт лёгкую красную обводку самой
  ноды (`.has-error-badge`) - НЕ вместо плашки, а вместе с ней. Отдельное
  комбо-правило `.has-error-badge.inspector-selected`, чтобы выбор ноды
  боковой панелью визуально не спорил с обводкой ошибки.
- Бейджи НЕ сериализуются в `.ncp` - отражение текущего состояния графа
  (или свойства типа), пересчитываются заново при каждой загрузке.

  свежая и всё ещё меняющаяся нода на данный момент.

## Раунд 25 — фикс двойного скролла (Table/Gantt), свободный ресайз Гантта, номера строк, ошибка соединения
- **Найдена и исправлена настоящая причина "двойного скролла" в
  `tableViewerNode.js`.** `.table-viewer-wrap` использовал сокращённую
  запись `overflow: auto;` (обе оси разом), а `.table-viewer-body-scroll`
  внутри - свой отдельный `overflow-y: auto`. При свободном ресайзе
  высота ставилась именно на `wrap` (`applyFreeResize`) - и он получал
  СВОЙ вертикальный скролл поверх внутреннего: один двигал шапку+тело+
  итог целиком, другой - только строки. Фикс: `wrap` теперь
  `overflow-x: auto; overflow-y: hidden;` (только горизонталь),
  `beginFreeResize`/`applyFreeResize` и сохранённая `wrapHeight`
  переведены на `bodyScroll` - единственное место, отвечающее за
  вертикальный скролл. Заодно источником истины для "есть ли ручной
  размер" стало JS-свойство `this.wrapHeight`, а не инспекция инлайн-
  стилей DOM (`wrap.style.width||height`) - целилась не в тот элемент.
- **`ganttNode.js` получил тот же паттерн свободного ресайза**, что
  `tableViewerNode.js` - `beginFreeResize`/`applyFreeResize`, нацеленные
  на `.gantt-rows-scroll` (единственную часть со своим вертикальным
  скроллом) - сразу правильно, без промежуточного бага, по свежему
  уроку из tableViewerNode.js. `wrapHeight` сериализуется в `.ncp`.
- **Столбец номеров строк** в `GanttNode` (`.gantt-row-num`, как в
  Excel/`tableViewerNode.js`) - ширина считается по числу цифр в
  количестве задач. Потребовало протащить объединённую ширину "номер +
  имя" (`leftWidth`) через все методы построения шапки/сетки/дедлайна,
  где раньше был захардкожен голый `LABEL_WIDTH`.
- **Сокет "any" переосмыслен как прокси, а не безусловное "true".**
  `constants.js`: `SOCKET_KINDS` - список всех известных родов сокета.
  `connectionManager.js`: совместимость `any` теперь проверяется
  перебором (`Constants.SOCKET_KINDS.includes(kind)`), а не одним
  условием "sourceKind === 'any' || targetKind === 'any'" - результат
  для текущего набора родов тот же самый (любой тип подходит), но
  архитектурно это прокси с явным списком допустимых родов, а не дыра в
  проверке - при необходимости "any" с ОГРАНИЧЕННЫМ подмножеством родов
  понадобится поменять только список, не логику.
- **Новое: ошибка на уровне КОНКРЕТНОГО соединения**, не всей ноды.
  `connectionManager.setConnectionError(sourceId, targetId, targetSocket,
  hasError, message)` - выставляет/снимает `hasError`/`errorMessage` на
  соединении, `renderer.createConnectionPath()` красит линию в красный
  (`#ef5350`) при `conn.hasError`, независимо от рода сокета, и переносит
  `errorMessage` в `title` хитбокса линии. Отличие от системы бейджей
  (Раунд 24): бейдж говорит "с этой нодой что-то не так" в целом, а это -
  "именно ЭТА связь не годится" - важно для будущих нод с несколькими
  `any`-входами, где нужно понимать, какой именно вход проблемный.
  Инфраструктура готова заранее, до появления первого живого потребителя
  (`DashboardNode`, фаза 1 плана Досок) - так же, как систему бейджей
  строили до того, как появился первый узел, которому она понадобилась.

## Раунд 26 — ретрофит PercentageNode/GanttNode на единый any-сокет

  Data) заменены одним универсальным (`isAny: true`) - нода сама

## Раунд 30 — исправлено переключение между стеками Листов и Досок
- **Причина бага**: `layoutManager.activeLayoutId` и
  `boardManager.activeBoardId` — два независимых стека, и каждый клик по

  Доска) и просто ничего не делал — граф нод не показывался, хотя на
  экране всё ещё была Доска.
- Добавлен флаг `viewActive` в `LayoutManager` и `BoardManager` — "сейчас
  на экране действительно мой вид (граф нод / Доска), а не просто я
  последним был активен в своём стеке". Оба менеджера обращаются друг к
  другу через `window.layoutManager`/`window.boardManager` (тот же паттерн,
  что уже использовался для переключения `#workspace`/`#boardCanvasWrap`)
  и сбрасывают чужой `viewActive` при переключении на свой вид.
- Клик по вкладке теперь переключает, если это другой лист/доска, ИЛИ
  тот же id формально активен, но `viewActive === false` (вид закрыт
  соседним стеком).
- CSS-класс `active` на вкладке тоже теперь требует `viewActive`, а не
  только совпадения id — раньше при переключении на Доску вкладка листа
  могла визуально остаться подсвеченной как активная одновременно с
  вкладкой доски.
- Переименование по двойному клику (`startRenameTab`) теперь тоже
  проверяет реальную видимость вкладки, а не только совпадение id.

## Раунд 32 — сетка Доски + ручки резайза виджетов + редактируемое Число
- **Холст Доски переведён с flex-column на CSS Grid** (`.board-page`):
  12 колонок (`GRID_COLS`, зеркало Bootstrap/Looker Studio), фиксированная
  высота ряда `ROW_PX = 24px`, `grid-auto-rows: minmax(ROW_PX, auto)` -
  виджет без ручного resize по-прежнему растягивается по высоте контента
  сам, ничего не сломалось для существующих проектов (colSpan по
  умолчанию = 12, во всю ширину, как раньше `width:100%`).
- **`DashboardNode.widgetLayout`** - новое поле (`{colSpan, rowSpan}`),
  `rowSpan: null` = авто-высота. Как и `widgetStyle` (Раунд 31),
  передаётся в `boardManager.registerWidget()` ПО ССЫЛКЕ - резайз
  применяется на Доске сразу, даже если нода "Дашборд" сейчас на
  неактивном Листе. Сериализуется вместе с остальными полями узла.
- **4 ручки на серединах граней** (`.board-widget-handle-n/e/s/w`) -
  рисуются только у ВЫБРАННОГО виджета (см. Раунд 31, клик по виджету).
  Восток/запад меняют `colSpan`, север/юг - `rowSpan`, шаг перетаскивания
  переводится в px через актуальную ширину страницы
  (`getComputedStyle`, без ручного хардкода). Во время перетаскивания
  меняется только инлайн-стиль самого виджета (мгновенный отклик без
  пересборки Доски на каждый pixel мыши); полный `renderActiveBoard()` -
  один раз на `mouseup`, чтобы соседние виджеты корректно перетекли на
  новое место сетки (`grid-auto-flow` браузера, без ручной collision-логики).
- **`NumberNode.getDashboardWidget()` теперь рендерит `<input>`, а не
  текст** - правки сразу пишутся в `this.value` через тот же
  `setValue()`, которым пользуется поле ввода самой ноды в графе (та же
  логика: `updateListData`, обновление DOM ноды в графе, если она
  отрисована, `nodeManager.calculateAll()`). У поля ввода
  `mousedown`/`click` останавливают всплытие - иначе первый клик в поле
  триггерил бы `selectWidget()` → полную пересборку Доски
  (`renderActiveBoard`) прямо в момент получения фокуса, и поле тут же
  теряло бы фокус, не успев его получить. Выбрать виджет (ручки/панель
  стиля) по-прежнему можно кликом рядом - по подложке/заголовку.
- **Известное ограничение (не ново, то же самое, что у `widgetStyle`)**:
  правки, идущие через `nodeManager.calculateAll()` (а не через прямую
  ссылку), пересчитывают только АКТИВНЫЙ (загруженный в `nodeManager`)
  Лист - если нода "Дашборд"/её источник живут на другом Листе, соседние
  виджеты на той же Доске не обновятся, пока тот Лист не станет активным
  хотя бы раз. Полноценный пересчёт графа по ВСЕМ Листам сразу - отдельная
  архитектурная задача, не в рамках 1.5.0.

## Раунд 37 — редактируемые виджеты (Число/Строка/Список) + важный фикс потери фокуса на Доске
- **Найден и исправлен реальный баг, скрытый с Раунда 32.** Любая правка
  в виджете идёт по цепочке `node.setValue()`/`recalculate()` →
  `nodeManager.calculateAll()` → `DashboardNode.calculate()` →
  `registerWidget()` → `boardManager.renderActiveBoard()` (см.
  dashboardNode.js). `renderActiveBoard()` раньше БЕЗУСЛОВНО делала
  `container.innerHTML = ''` и пересобирала все виджеты заново - при
  вводе в поле Числа это означало, что сам `<input>`, в который печатает
  пользователь, уничтожался и создавался заново НА КАЖДОЕ НАЖАТИЕ
  КЛАВИШИ, сбрасывая фокус. Раньше это осталось незамеченным (виджет
  Числа проверялся только статически, не в реальном вводе) - вскрылось
  при попытке сделать МНОГОПОЛЬНЫЙ виджет Списка, где было бы совсем
  плохо (перепрыгивающий фокус после каждого символа в любом из полей).
  - Исправление - `renderActiveBoard()` теперь реконсилирует DOM ПО МЕСТУ
    вместо `innerHTML=''`: если сейчас фокус внутри поля какого-то
    виджета, его DOM-узел переиспользуется КАК ЕСТЬ (не пересоздаётся) -
    `page.insertBefore()`/`removeChild()` двигают узлы уже прикреплённой
    к документу страницы, не отсоединяя их от документа ни на миг (в
    отличие от `innerHTML=''`, которая уничтожает и создаёт заново ВСЕ
    DOM-объекты). Остальные виджеты на Доске по-прежнему пересобираются
    заново при каждом вызове - живое обновление (например, Таблица,
    получающая изменённое число через "Дашборд") работает как и раньше,
    без изменений.
- **`StringNode.getDashboardWidget()`** теперь `<input type="text">`, а
  не текст - точный аналог `NumberNode` (Раунд 32): правки сразу пишут в
  `this.value` через тот же `setValue()`, что и поле ввода ноды в графе.
- **`ListInputNode.getDashboardWidget()`** теперь таблица с ДВУМЯ `input`
  на строку (имя + значение) - аналог `renderRows()` в теле самой ноды.
  Правки пишут прямо в `this.items[i]` и вызывают `recalculate()`.
  Добавление/удаление строк прямо с Доски - осознанно не в этом раунде
  (см. "Заметки на будущее"), сейчас редактируются только уже
  существующие строки.
  - Значения показываются СЫРЫМИ числами в поле ввода, не через
    `Helpers.formatByType()` (как раньше в статичной версии) - поле
    редактирования должно показывать то, что можно ввести обратно
    (`1000`), а не отформatированную строку (`1 000 ₽`), которую
    `parseFloat()` не распарсит корректно.
  - Все input-поля виджетов останавливают всплытие `mousedown`/`click` -
    тот же приём, что у `NumberNode` (Раунд 32): иначе клик в поле
    триггерил бы `selectWidget()` в довесок к вводу текста (не критично
    само по себе, но избыточно).
- **Архитектура сквозной передачи данных не менялась и не нуждалась в
  правках** - `DashboardNode.calculate()` уже с Раунда 27 пробрасывает
  `value`/`listData`/`tableData` от источника насквозь на свой выходной
  сокет (`any`), поэтому цепочка вида Число → Дашборд → Таблица (правка
  Числа прямо в виджете подхватывается столбцом Таблицы) уже работала на
  уровне данных - не хватало только (а) самой возможности редактировать
  виджет и (б) вот этого фикса потери фокуса. Многопроходный
  `nodeManager.calculateAll()` сам распространяет изменение по цепочке
  произвольной длины в пределах активного Листа - никакой отдельной
  "магии" для конкретно этой цепочки строить не пришлось, тот же
  механизм будет работать для любого источника, который передаётся через
  "Дашборд" дальше по графу.

## Раунд 38 — переопределение значения на Доске больше не трогает исходную ноду
- **Баг, о котором сообщил Mr.D**: цепочка Число → Дашборд → Диаграмма не
  подхватывала изменение числа, сделанное прямо в виджете на Доске.
- **Найдена настоящая механическая причина** - она глубже, чем казалось
  в Раунде 37. `NumberNode.getDashboardWidget()` дёргал `node.setValue(val)`,
  который выставляет `this.value = val` и зовёт `nodeManager.calculateAll()`.
  Но `calculateAll()` ПЕРВЫМ ШАГОМ, ДО пересчёта остальных нод, проходит
  по всем нодам типа `number` и вызывает `updateValueFromInput()` -
  а этот метод читает значение ЗАНОВО ИЗ DOM-ПОЛЯ САМОЙ НОДЫ В ГРАФЕ
  (`.number-input-compact`), которое виджет на Доске не трогал вообще
  (это два разных DOM-элемента). В итоге `this.value`, только что
  выставленный из виджета, тут же перезаписывался обратно старым
  значением из графа - ДО того, как `DashboardNode.calculate()` успевал
  его прочитать на этом же проходе. Число в узле графа при этом
  оставалось прежним - визуально казалось, что "ничего не произошло".
- **Правильное архитектурное решение - то, что предложил Mr.D**:
  редактирование виджета больше НЕ трогает исходную ноду вообще. Вместо
  этого пишет в `DashboardNode.overrideValue` + `DashboardNode.overridden`
  (см. новый докстринг класса в `dashboardNode.js`) - пока `overridden`
  включён, СВОЙ выход (`value`/`listData`/`tableData`) `DashboardNode`
  строит из `overrideValue`, а не пробрасывает источник насквозь. Это
  заодно и чинит механический баг выше - `NumberNode.value` больше не
  трогается редактированием на Доске, значит `updateValueFromInput()`
  нечего перезаписывать не по адресу.
- **Контракт `getDashboardWidget()` расширен третьим необязательным
  параметром `ctx`** (`numberNode.js`/`stringNode.js`/`listInputNode.js`):
  - `ctx.readOnly` - источник обязан нарисовать виджет БЕЗ полей ввода
    (просто текст), если `DashboardNode.locked === true`
  - `ctx.overrideValue` - если задан (не `undefined`), источник должен
    показывать ЕГО вместо своего собственного `this.value`/`this.items`
  - `ctx.onEdit(value)` - источник обязан звать ЭТО вместо прямой записи
    в себя; `value` - число/строка для Числа/Строки, массив `{name,value}`
    целиком для Списка (см. `ListInputNode` - при каждой правке любой
    ячейки уходит полный обновлённый массив, не дельта)
  - Без `ctx` (старый вызов) поведение как раньше (фолбэк на
    `node.setValue()`/`node.recalculate()`) - на случай, если
    `getDashboardWidget()` когда-нибудь вызовут не из `DashboardNode`.
- **Два новых флага на `DashboardNode`** (боковая панель, секция
  "Переопределение значения"):
  - **"Значение переопределено на Доске"** (`overridden`) - включается
    АВТОМАТИЧЕСКИ первой же правкой виджета. В панели можно только
    СНЯТЬ его - это возвращает выход `DashboardNode` к живому значению
    источника (тот же `overridden=false` сбрасывает `overrideValue`).
    Дополнительно - маленькая пометка "✎" в углу самого виджета на
    Доске (`boardManager.buildWidgetEl`) и info-бейдж над нодой в графе.
  - **"Нередактируемая"** (`locked`) - запрещает редактирование виджета
    на Доске вообще (`ctx.readOnly`), независимо от `overridden`.
  - Оба флага, `overrideValue`, сериализуются вместе с остальными полями
    `DashboardNode`.
- Переопределение сбрасывается автоматически, если поменять само
  соединение (подключить к `DashboardNode` другой источник) - старое
  `overrideValue` относилось к прежней ноде и теряет смысл. Отслеживается
  по `_lastSrcId` (не сериализуется намеренно - id последнего источника,
  который видели на предыдущем `calculate()`; `undefined` вместо `null`
  для маркера "ещё не считали ни разу" - иначе восстановленное из файла
  переопределение сбрасывалось бы на первом же пересчёте после загрузки).

## Раунд 39 — визуальный проход по Доске: ориентир Google-дашборды (закрывает 1.5.0)
- **Главный пробел**: у виджетов до этого раунда фактически не было
  собственного "тела карточки" - `padding: 4px; margin: -4px;` и никакого
  фона, кроме фона страницы. Каждый виджет визуально был просто текстом,
  лежащим на странице, а не самостоятельной плиткой - непохоже на
  Looker Studio/Google Data Studio, где каждый виджет однозначно читается
  как отдельная приподнятая карточка.
- **`.board-widget` теперь настоящая карточка**: свой фон
  (`--md-surface-3`), скругление (`--md-radius`), реальные внутренние
  отступы (16×18px), тень (`--md-elevation`), лёгкий подъём + более
  глубокая тень по hover. Цветная полоса сверху (3px) - тот же акцентный
  цвет, что уже красит число/шапку таблицы (`--board-widget-accent`,
  Раунд 31) - если цвет не задан, полоса прозрачная и не видна.
  - **Важный нюанс при выборе фона**: `--md-surface-2` оказался БУКВАЛЬНО
    тем же цветом, что и `--md-divider` (`#2d2d2d` у обоих) - на таком
    фоне разделители строк таблиц/списков внутри виджета стали бы
    полностью невидимы. Взял `--md-surface-3` (`#3d3d3d`) - следующая
    по шкале приподнятости поверхность, и разделители на ней снова видны.
- **Найден и исправлен попутный баг из Раунда 32**: `.board-empty`
  (заглушка "на этой доске пока нет виджетов") после перехода `.board-page`

## Раунд 41 — новая нода "Импорт из Excel" (xlsxImportNode.js)
- **Без сторонних библиотек - осознанно.** В проекте нет `package.json`/
  `node_modules`, а сеть в текущей сборке недоступна - тянуть SheetJS
  или аналоги неоткуда. `.xlsx` - это ZIP-архив с XML внутри (OOXML), а
  всё нужное для его чтения уже есть в самом Chromium/Electron:
  - разбор ZIP (центральный каталог, локальные заголовки) - написан с
    нуля вручную по спецификации (APPNOTE.TXT), формат простой;
  - расжатие DEFLATE - через нативный `DecompressionStream('deflate-raw')`,
    свою реализацию inflate писать не пришлось;
  - разбор самих XML (`workbook.xml`/`sheetN.xml`/`sharedStrings.xml`) -
    через нативный `DOMParser`, а не самописный XML-парсер.
  - Новый файл `src/js/utils/xlsxReader.js` - весь этот код, без единой
    внешней зависимости.
- **Проверено не "на глаз"**: вручную собраны настоящие валидные .xlsx
  (побайтово корректный ZIP - центральный каталог, локальные заголовки,
  CRC32) с разными сценариями (несколько листов, shared strings, inline-
  строки, смешанные методы сжатия - deflate И без сжатия в одном архиве,
  разреженные ячейки/пропуски в середине строки, отсутствующий
  `workbook.xml.rels`, заведомо не-ZIP файл) и прогнан весь модуль
  `xlsxReader.js` в Node против них (с мини-заглушкой `DOMParser`, т.к.
  в самом Node его нет) - все сценарии дали ожидаемый результат,
  включая корректную обработку ошибок на битом/не-ZIP файле.
- **Два явных шага - специально, чтобы НЕ разбирать весь .xlsx на каждый
  пересчёт графа** (то, о чём просил Mr.D):
  1. "Выбрать файл" (кнопка в теле ноды) - `XlsxReader.scanOutline()`:
     имена листов + ТОЛЬКО первая строка (заголовки) каждого. Быстро, но
     не совсем "бесплатно" - XML лист всё равно приходится расжать
     целиком (DEFLATE нельзя размотать частично, только с начала потока) -
     просто не строится из него ничего, кроме заголовков.
  2. "Импортировать выбранное" (боковая панель - выбор листа + галочки
     нужных столбцов, новый `type: 'button'` в `InspectorManager`,
     раньше такого типа поля не было) - `XlsxReader.readSheet()`
     разбирает ТОЛЬКО выбранный лист целиком, и в ноде остаются ТОЛЬКО
     выбранные столбцы (`importedHeaders`/`importedRows`).
  - `calculate()` не делает вообще ничего с файлом - просто отдаёт то,
    что уже импортировано на шаге 2. Сырые байты файла (`_arrayBuffer`)
    и результат поверхностного сканирования (`_outline`) - ТРАНЗИТНОЕ
    состояние текущей сессии, НЕ сериализуются (раздули бы `.ncp`-файл и
    задублировали то, что и так есть на диске) - после загрузки проекта
    нужно заново выбрать файл, чтобы сменить лист/столбцы, но уже
    импортированные данные переживают сохранение/загрузку как обычные
    данные ноды (тот же принцип, что у `ListInputNode.items`).
- **`InspectorManager`: новый тип поля `'button'`** - разовое действие
  (`field.onClick`, может быть асинхронным), а не значение для чтения/
  записи через `get()`/`set()` - рендерится на всю ширину, без подписи
  слева (`.inspector-action-btn`, добавлен в ОБЕ темы).
- **Известные упрощения** (см. также докстринг `XlsxReader`):
  - Даты приходят как числа (серийный день от начала эпохи Excel) - сам
    формат ячейки (что это дата, а не число) хранится в `styles.xml`,
    который не разбирается - полноценная поддержка дат осталась бы
    отдельной задачей (разбор `numFmt`/`styles.xml`).
  - Первая строка листа всегда считается заголовками - переключателя
    "без заголовков" нет.
  - Старый бинарный `.xls` не читается, только `.xlsx` (Office Open XML).
  - ZIP64 (архивы >4GB или >65535 файлов) не поддержан - для `.xlsx`
    такого размера это практически нереальный сценарий.

    `TableInjectNode`/`TableRemoveNode`) и зебра/линии строк/линии
    столбцов. Подключается ПОСЛЕ любой Data-ноды (`TableNode`,
    `ChartNode`, `XlsxImportNode`, `TableInjectNode`, `TableRemoveNode` -
    какой угодно источник) - оформление больше не привязано к тому,
    ЧТО строит/меняет таблицу, а работает как отдельный шаг в цепочке.
  - `TableWidgetRenderer` не менялся - он и раньше принимал ноду
    (`node.boardZebra` и т.п.), а не таблицу напрямую, поэтому ноды без
    этих полей просто получают `undefined` (= выключено) без единой
    правки в самом рендерере.
- **2. Явная строка заголовков в `XlsxImportNode`** - раньше первая
  строка листа ВСЕГДА считалась заголовками; в реальных файлах часто
  выше есть строка с названием отчёта, пустая строка-отступ и т.п.
  - **`XlsxReader.getHeadersAtRow(arrayBuffer, outline, sheetPath, rowIndex)`**
    (новый метод) - достаёт заголовки с ЛЮБОЙ явно указанной строки, не
    только первой. Расжимает заново только ОДИН нужный лист (entries/
    sharedStrings переиспользуются из `outline`), а не весь файл целиком.
  - Новое поле панели "Строка заголовков (с 1)" у `XlsxImportNode` -
    меняет `this.headerRow`, асинхронно перечитывает заголовки текущего
    листа и сбрасывает выбор столбцов (новая строка может иметь другой
    набор). Тот же перерасчёт срабатывает и при смене ЛИСТА, если
    `headerRow != 1` - иначе переключение на другой лист молча показало
    бы заголовки с первой строки, а не с настроенной.
  - `_importSelected()` теперь режет данные по `this.headerRow`, а не по
    захардкоженной `1`.
- **Важная находка при написании тестов для пункта 2 - реальный баг,
  выявленный ДО релиза.** Строки в `.xlsx` адресуются атрибутом `r="N"` у
  `<row>`, а НЕ порядковой позицией `<row>`-элемента в XML - Excel не
  обязан записывать полностью пустые строки. Старый код
  (`rowEls[rowIndex]`, `rowEls.map(...)`) брал строку ПО ПОЗИЦИИ в
  массиве `<row>`-элементов - если, скажем, строка 2 пустая и Excel её
  не записал, третий по счёту `<row>` в файле имеет `r="4"`, а не `r="3"`,
  и "строка 3" в понимании пользователя тихо превращалась бы в "строка 4"
  без какой-либо ошибки. Собрал тестовый `.xlsx` именно с такой дырой
  (заголовок отчёта в строке 1, ПУСТАЯ строка 2 без `<row>` в XML вовсе,
  настоящие заголовки в строке 3) - без исправления тест ловил
  рассинхронизацию сразу. Добавлен `parseSheetRows()` - собирает строки
  ПО НАСТОЯЩЕМУ номеру (`r`), с пустыми массивами на месте пропущенных -
  используется везде, где раньше был порядковый доступ (`scanOutline`,
  `readSheet`, `getHeadersAtRow`). Это чинит не только новую функцию
  строки заголовков, но и ПОВЕДЕНИЕ ИЗ РАУНДА 41 (обычный импорт без
  указания строки заголовков), которое было уязвимо к той же проблеме с
  самого начала, просто ещё не было замечено.

## Раунд 45 — три новых операционных узла для таблиц
- **Все три протестированы АЛГОРИТМИЧЕСКИ ОТДЕЛЬНО** (чистая логика в
  Node, без DOM/BaseNode) ДО того, как писать сами ноды - тот же подход,
  что уже пару раз ловил реальные баги в этом проекте (Раунды 41/44).
  На этот раз все три алгоритма прошли проверку сразу без находок.
- **1. `TableMergeColumnsNode` ("Объединение столбцов")** - Data → Data,
  один вход. Берёт несколько столбцов (галочки в панели) и схлопывает их
  в ОДИН, вставленный на указанную позицию среди ОСТАВШИХСЯ столбцов:
  - "Объединить" - конкатенация значений строки через разделитель
    (по умолчанию `.`), результат - текст;
  - "Сумма" - арифметическая сумма значений строки, результат - число.
  - Название результирующего столбца - авто (из объединённых заголовков)
    или своё, если задано в панели.
  - `this._inputHeaders` - снимок заголовков ВХОДА, сделанный в начале
    `calculate()` до объединения - специально для чекбоксов в панели:
    после объединения в `this.tableData` уже МЕНЬШЕ столбцов, чем на входе.
- **2. `TableJoinNode` ("Слияние таблиц")** - Data → Data, два входа
  (А - базовая, Б - присоединяемая). LEFT JOIN по ключевым столбцам
  (свой ключ у каждой таблицы, оба выбираются в панели) - но, в отличие
  от обычного JOIN, у Б может быть НЕСКОЛЬКО строк с одним ключом (или
  вовсе ни одной), поэтому все столбцы Б (кроме ключа) сворачиваются в
  ОДНО значение на строку А через ОДНУ операцию агрегации (одна и та же
  для всех столбцов Б - именно так, как описал Mr.D, не по столбцу):
  Сумма/Максимум/Минимум/Среднее/Первое значение/"Перечислить
  одинаковые" (список уникальных значений среди совпадений, текстом).
  Строки А без единого совпадения в Б не теряются - просто получают
  "пустой" результат агрегации (0 для суммы, `null` для
  макс/мин/среднего, пустая строка для перечня).
- **3. `TableFilterNode` ("Отсеять")** - Data → Data, один вход.
  Формирует новую таблицу, оставляя только строки, подходящие ПОД ВСЕ
  заданные условия (по одному текстовому полю на столбец в панели,
  пусто = без условия). Вид условия определяется автоматически:
  - строка вида `>30`, `<=10`, `!=0` и т.п. - СРАВНЕНИЕ (числом, если
    ячейка - число и правая часть тоже похожа на число, иначе текстом,
    регистронезависимо);
  - иначе - ПЕРЕЧЕНЬ значений через запятую (`0, 1, 5` / `Вася, Лена`) -
    строка проходит, если ячейка совпадает с ЛЮБЫМ из перечня.
  - Ровно пример из ТЗ Mr.D (`[0,1,5]`/`[Вася,Лена]`/`[>30]`) - и есть
    первый тестовый сценарий, который прогонялся перед тем, как писать
    саму ноду.
- **Все три - тот же паттерн, что у `TableInjectNode`/`TableRemoveNode`/
  `TableFormatNode`** (Раунды 42/44): минимальное тело (сокеты + краткая
  сводка операции текстом), вся настройка - в панели, виджет Доски через
  общий `TableWidgetRenderer` (только номера строк/сортировка -
  оформление намеренно осталось только у `TableFormatNode`, см. Раунд 44 -
  разделение работает и здесь, три новые ноды не хламятся зеброй/линиями).
  Добавлен общий список `TABLE_WIDGET_TYPES` в `layoutManager.js`, чтобы
  не повторять один и тот же список типов нод в каждой строке сериализации.

## Раунд 46 — TableJoinNode: агрегация по каждому столбцу Б + исключение столбцов
- Проверено алгоритмически отдельно ДО правки самой ноды (тот же подход,
  что и в Раунде 45) - три сценария: разная агрегация на разные столбцы Б
  одновременно, исключение НЕ ключевого столбца А, и попытка исключить
  ключевой столбец (должна быть проигнорирована - ключ обязателен). Все
  три прошли сразу.
- **Агрегация - теперь на каждый столбец Б своя**, а не одна общая, как
  было в Раунде 45. `this.aggregation` (одно поле на всю ноду) заменено
  на `this.columnConfigB[i].aggregation` - у каждого столбца Б свой выбор
  (Сумма/Максимум/Минимум/Среднее/Первое значение/Перечислить одинаковые).
- **Столбцы (кроме ключевого) теперь можно убирать из результата** -
  и у А, и у Б, не только у Б: `columnConfigA[i].include`/
  `columnConfigB[i].include`, чекбокс на каждый столбец в панели.
  Ключевые столбцы (А и Б) в панели НЕ показываются вовсе - ключ А
  обязателен структурно (без него нет смысла в строках результата),
  ключ Б и так никогда не дублируется в выходе.
- **Индексация `columnConfigA`/`columnConfigB` - по индексу столбца В
  ИСХОДНОЙ таблице**, а не по порядку в результате - так настройки не
  съезжают, если сменить ключевой столбец (тот же принцип, что уже был у
  `columnStyles` в `TableFormatNode`, Раунд 44). Синхронизация по длине -
  тот же приём: лишнее обрезается, недостающее добавляется с дефолтами
  (`include: true`, у Б ещё `aggregation: 'first'`).
- Раньше единственный select "Операция (одна для всех столбцов Б)"
  заменён на: для каждого столбца Б - подраздел с чекбоксом "Включить в
  результат" + отдельный select "Агрегация"; для каждого столбца А
  (кроме ключа) - просто чекбокс "включить/убрать".

# Заметки на будущее (не реализовано, зафиксировано для следующих раундов)

- **`GanttNode`: список праздников (сверх суббот/воскресений) не

  источника праздников для всех локалей нет.

# Новые возможности (v1.2.0)


## Новые типы сокетов: String и Data
- `socketFactory.js`: добавлены опции `isString`/`isData`; каждый сокет
  теперь получает единый `data-kind` (`list`/`string`/`data`/`count`/`plain`).
- `connectionManager.js`: проверка совместимости при соединении обобщена
  с булева `isList` на произвольный "род" сокета — строка соединяется
  только со строкой, данные только с данными, список только со списком;
  `count` остаётся псевдонимом обычного числа (как было исторически).
- `renderer.js`: цвет соединительной линии и подсветка сокета учитывают
  новые роды (String — синий круг `#64b5f6`, Data — оранжевый ромб `#ff8a65`).
- `dataTypes.js`: добавлен класс `TableData` (колонки, `rowCount`,
  `toListData()` — сворачивает таблицу обратно в привычный список).
- `baseNode.js`: добавлен необязательный хук `getValueFormat()` —
  источник значения может сообщить формат (`number`/`currency`/`percent`,
  см. `Constants.VALUE_FORMATS`), потребители читают его вместо жёсткого
  предположения "это всегда просто число".

## Нода String (`stringNode.js`)
- Компактная служебная нода: одно текстовое поле, один выход типа String.
- Предназначена для заголовков/подписей — например, заголовков колонок
  таблицы.

## Нода Table (`tableNode.js`)
- Обработчик: собирает несколько LIST-входов в столбцы таблицы.
- У каждого столбца два входа — LIST (обязательный) и String
  (необязательный, переопределяет заголовок столбца) — с уникальными
  индексами сокетов на столбец (см. docs/NODE_API.md, раздел 5).
- Автодобавление нового пустого столбца по заполнении последнего
  (паттерн `checkAndAddEmptySlot`/`rerender` из `operationNode.js`).
- У колонки можно вручную выбрать формат (Авто/Число/Деньги/Проценты);
  при "Авто" формат наследуется от `getValueFormat()` источника-списка.
- Выход — сокет типа Data с готовой `TableData`.
- Сериализация: `columns`/`_nextIndex` добавлены в `layoutManager.serialize()`.

## percentageNode — второй вход Data
- Добавлен второй, альтернативный вход (Data, index 1) — если подключены
  оба входа одновременно, побеждает Data (у него уже есть явные заголовки
  колонок из String).
- Легенда диаграммы показывает значение с учётом формата колонки
  (`1000 ₽ (40.0%)` вместо голого процента).
