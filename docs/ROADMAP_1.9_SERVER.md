# Серверная часть и совместная работа — черновик для 1.9

Статус: **планирование, ничего не реализовано**. Зафиксировано по
запросу Mr.D ("давай сделаем серверную часть... докер с линуксом,
БД, менеджмент обмена данных для совместной работы... пока накидаем
как перспективные работы для обновления 1.9") — рабочий черновик,
предназначен для обсуждения и уточнения ПЕРЕД началом реализации, не
финальная спецификация.

---

## 1. Зачем и что именно решаем

NodeCalculate сейчас — **полностью локальное** desktop-приложение:
один пользователь, один компьютер, файл `.ncp` на диске. Цель этого
раздела — дать нескольким людям работать с ОДНИМ и тем же проектом,
храня его на сервере, а не только на диске одного человека.

Важно сразу разделить ДВЕ разные по сложности задачи, которые легко
смешать в одну фразу "совместная работа":

- **(А) Доступ к общему проекту с разных машин** — Иван сохранил
  проект на сервер вечером, Мария утром открыла ЕГО ЖЕ на своём
  компьютере и продолжила работу. Не обязательно ОДНОВРЕМЕННО.
- **(Б) Настоящее одновременное редактирование** — Иван и Мария
  одновременно смотрят на ОДНУ и ту же Диаграмму Ганта, и оба видят
  правки друг друга почти сразу (как в Google Docs/Figma).

(А) — на порядок проще и должна быть частью 1.9 целиком. (Б) — самая
сложная часть темы "совместной работы" в индустрии (требует
CRDT/Operational Transformation для КОРРЕКТНОГО слияния одновременных
правок без потери данных) — ниже предложен ПРОМЕЖУТОЧНЫЙ, гораздо
более достижимый вариант (см. раздел 4), не настоящий CRDT, но и не
наивное "кто сохранил последним, тот и прав".

## 2. Развёртывание — Docker на Linux

```
docker-compose.yml
├── db          PostgreSQL (проекты/пользователи/дельты)
├── api         Node.js (тот же язык, что и клиент — см. раздел 6)
└── proxy       (опционально) nginx/Caddy - TLS-терминация, раздача статики
```

Почему PostgreSQL, а не что-то более "модное" (MongoDB и т.п.):
пользователи/права доступа/участники проекта — классические
реляционные связи (many-to-many), а сами данные проекта (граф нод) —
и так уже JSON (формат `.ncp`) — PostgreSQL с типом `JSONB` даёt
одновременно и реляционные связи, и удобное хранение JSON-блобов без
необходимости поднимать вторую, отдельную БД.

Почему Node.js для сервера, а не что-то ещё: клиент (Electron) уже
целиком на JS — движок diff/patch (`stateDiff.js`, Раунд 196) можно
БУКВАЛЬНО переиспользовать НА СЕРВЕРЕ без переписывания на другой
язык — сервер сможет вычислять/проверять те же дельты, что и клиент,
той же самой, уже протестированной (2000+ fuzz-итераций) логикой.

## 3. Набросок схемы БД

```sql
users            (id, username, password_hash, created_at)
projects         (id, name, owner_id, created_at, updated_at)
project_members  (project_id, user_id, role)  -- role: owner | editor | viewer
snapshots        (id, project_id, data JSONB, version, created_at, author_id)
deltas           (id, project_id, base_snapshot_id, diff JSONB,
                   author_id, created_at)
```

- `snapshots` — периодические ПОЛНЫЕ срезы (та же структура, что уже
  производит `layoutManager.serialize()` + `boardManager.serialize()`
  — ничего нового изобретать не нужно, это УЖЕ готовый формат).
- `deltas` — дельты МЕЖДУ снимками, в ТОМ ЖЕ формате, что уже
  производит `stateDiff.js` (`computeDiff()`) — сервер хранит
  "снимок + цепочка дельт после него", периодически "схлопывая"
  старые дельты в новый снимок (та же логика, что уже применяется
  локально для дельта-журнала Undo/Redo, Раунд 196 — только теперь
  ещё и по сети).

## 4. Модель синхронизации — три уровня сложности

### Уровень 1 (рекомендуется для 1.9) — "общий диск с историей"
Пользователь явно жмёт "Отправить на сервер"/"Получить с сервера" (по
аналогии с git push/pull, не автоматическая синхронизация в реальном
времени). Конфликты возможны, но РЕДКИ (нужно, чтобы два человека
одновременно отправили СВОИ изменения без предварительного "pull") —
решаются просто: сервер отклоняет push, если с момента ПОСЛЕДНЕГО
"pull" на сервере уже появилась чужая версия (та же механика, что у
git с "non-fast-forward" push) — пользователь сначала подтягивает
чужие изменения, видит, что изменилось, и подтверждает.

Плюсы: реализуемо в разумные сроки, минимальный риск потери данных
(сервер НИКОГДА не перезаписывает молча). Минусы: не "живое"
соредактирование — скорее "общая папка с историей версий".

### Уровень 2 — "слияние по полям" (использует уже готовый stateDiff.js)
Раз `computeDiff()` УЖЕ работает на уровне отдельных полей и
элементов массива по `id` (не переписывает весь проект целиком) —
можно пойти дальше git-модели: если Иван поправил Ноду А, а Мария
Ноду Б — это НЕ конфликт, можно слить ОБЕ дельты автоматически без
вопросов пользователю. Конфликтом считается ТОЛЬКО одновременная
правка ОДНОГО И ТОГО ЖЕ поля ОДНОЙ И ТОЙ ЖЕ ноды — такие случаи
относительно редки на практике (разные люди обычно работают над
разными частями графа) и могут решаться явным диалогом ("Иван
поменял X на 10, Мария — на 15, что оставить?").

Плюсы: гораздо ближе к "настоящей" совместной работе, не требует
блокировок. Минусы: заметно больше работы на сервере (нужна логика
трёхстороннего слияния - "общий предок + два потомка"), требует
аккуратного UI для конфликтов.

### Уровень 3 — настоящее реальное время (Figma/Google Docs style)
Требует CRDT (Conflict-free Replicated Data Types) или Operational
Transformation — оба ЗНАЧИТЕЛЬНО меняют то, КАК данные вообще
представлены внутри приложения (обычно НЕ "текущее состояние +
diff", а "журнал операций, коммутативных по построению") — фактически
ПОЛНОСТЬЮ ДРУГАЯ архитектура данных, не надстройка над существующей.
Не рекомендуется для 1.9 — отдельная, самостоятельная по объёму
задача, стоит рассматривать отдельно и только если Уровень 1/2
окажется недостаточным на практике.

**Рекомендация**: начать с Уровня 1 в 1.9, заложить архитектуру так,
чтобы Уровень 2 можно было добавить ПОЗЖЕ без переделки с нуля (см.
раздел 3 — формат `deltas` УЖЕ подходит для обоих уровней).

## 5. Набросок API

```
POST   /auth/login                     -> {token}
POST   /projects                       -> создать пустой проект на сервере
GET    /projects                       -> список проектов текущего пользователя
GET    /projects/:id/snapshot          -> последний полный снимок
POST   /projects/:id/push              -> отправить дельту (см. Уровень 1 - с проверкой "не устарела ли база")
GET    /projects/:id/deltas?since=X    -> получить дельты после снимка X ("pull")
POST   /projects/:id/members           -> пригласить участника (owner/editor/viewer)
WS     /projects/:id/presence          -> (опционально) кто сейчас смотрит на проект - "живые" индикаторы присутствия, БЕЗ синхронизации самих правок
```

`WS /presence` — отдельно от самой синхронизации данных: простой
"кто сейчас в проекте" список (типа "🟢 Иван, 🟢 Мария") — полезная,
относительно дешёвая в реализации штука, даже если сама
синхронизация данных остаётся на Уровне 1 (push/pull по кнопке).

## 6. Изменения на стороне клиента (Electron)

- Экран входа (логин/пароль или токен) - новое понятие "облачный
  проект" наравне с локальным файлом `.ncp`.
- В менеджере проектов (вкладка "Проекты" в настройках, Раунд 184) -
  РЯДОМ со списком локальных недавних файлов - список проектов НА
  СЕРВЕРЕ, к которым у пользователя есть доступ.
- Кнопки "Отправить на сервер"/"Получить с сервера" - используют ТОТ
  ЖЕ `stateDiff.js`, что уже посчитан для локальной истории
  Undo/Redo - клиент вычисляет diff между СВОИМ последним известным
  снимком с сервера и ТЕКУЩИМ локальным состоянием, отправляет ЕГО
  (не весь проект целиком).
- Работа полностью БЕЗ сервера должна остаться ПОЛНОСТЬЮ рабочей -
  серверная часть строго ОПЦИОНАЛЬНА, не заменяет локальный
  `.ncp`-файл, а дополняет его.

## 7. Безопасность (минимум для 1.9)

- TLS обязателен (через proxy-контейнер, не голый HTTP наружу).
- Пароли - хешированные (bcrypt/argon2), не хранить в открытом виде.
- Права участников проекта (`project_members.role`) проверяются на
  КАЖДЫЙ запрос сервера, не только при приглашении.
- Токены (JWT или аналог) с разумным сроком жизни + refresh.

## 8. Открытые вопросы (нужно обсудить до начала реализации)

1. Самостоятельный хостинг (тот самый Docker у Mr.D) или облачный
   провайдер как альтернатива/резерв?
2. Уровень 1 или сразу заложить Уровень 2 в схему БД (архитектурно
   разница небольшая, но влияет на объём работ уже в 1.9)?
3. Нужна ли работа офлайн с ПОСЛЕДУЮЩЕЙ синхронизацией (заготовил
   правки без сети, потом отправил), или предполагается, что сервер
   всегда доступен во время работы?
4. Как быть с крупными вложениями (например, ImageNode) - хранить
   бинарные данные в той же БД (`bytea`/`JSONB` с base64) или
   отдельным объектным хранилищем (S3-совместимым, например MinIO -
   тоже разворачивается в Docker)?
5. Нужна ли версия сервера как отдельно устанавливаемое ПО
   (самостоятельный релиз/образ), синхронизированная по номеру с
   версией клиента, или сервер живёт по СВОЕМУ собственному циклу
   версий, независимо от Electron-приложения?

## 9. Ориентировочная последовательность работ (для 1.9, Уровень 1)

1. Docker Compose: PostgreSQL + пустой Node.js API-каркас.
2. Схема БД (раздел 3) + миграции.
3. Аутентификация (`/auth/login`) + базовый CRUD проектов.
4. Перенос `stateDiff.js` в общий модуль, используемый И клиентом, И
   сервером (без дублирования кода).
5. `push`/`pull` эндпоинты + клиентская логика (раздел 6).
6. Список серверных проектов в UI менеджера проектов.
7. UI приглашения участников + права доступа.
8. (Опционально) presence через WebSocket.
